# 학습 노트: VM 네트워크, GPU 패스스루, btrfs 서브볼륨

`VM_PLAN.md`를 진행하면서 정리한 개념 설명.

## 1-1. VM 네트워크: 브리지, 라우팅, NAT

### 0. VirtualBox 기억 바로잡기: 192.168.56.x는 Host-only

- 호스트가 192.168.0.100이고 VM이 192.168.56.100이었다면, 그건 브리지 모드가 아니라 **Host-only 어댑터**였을 가능성이 높다.
- VirtualBox는 Host-only 네트워크를 만들면 호스트에 `vboxnet0` 인터페이스를 만든다. 기본 주소가 `192.168.56.1/24`다.
- VirtualBox의 자체 DHCP 서버가 VM에 192.168.56.x를 준다.
- 이 네트워크는 호스트와 VM만 연결한다. 인터넷으로 나가는 길은 없다.
- 그래서 흔히 VM에 NIC을 두 개 붙였다. **NAT 어댑터(10.0.2.15, 인터넷용)와 Host-only 어댑터(192.168.56.x, 호스트 접속용)** 조합이다.
- 진짜 브리지 모드였다면 VM도 공유기에서 **192.168.0.x**를 받는다.
- **우리 설계는 "Host-only + NAT"를 NIC 하나로 합친 것**이다.

### 1. 기초: L2와 L3

네트워크 통신에는 **주소가 두 종류**이고, 각각 담당하는 범위가 다르다.

| | L2 (데이터링크, 이더넷) | L3 (네트워크, IP) |
|---|---|---|
| 주소 | MAC (`88:36:6c:c1:0b:ff`) | IP (`192.168.0.1`) |
| 범위 | **같은 네트워크(같은 선/스위치) 안에서만** | 네트워크와 네트워크 사이 |
| 장비 | 스위치 | 라우터 |
| 데이터 단위 | 프레임 | 패킷 |

- **MAC**은 NIC 공장에서 붙인 번호다. "같은 스위치에 꽂힌 옆자리 기기"를 찾는 데 쓴다.
- **IP**는 논리적인 주소다. "지구 반대편 서버"까지 찾아가는 데 쓴다.
- 실제로 선을 타고 나가는 건 항상 **프레임**이다. IP 패킷은 프레임 안에 담긴 내용물이다.

```
 [ 이더넷 프레임                                                 ]
 [ 목적지 MAC | 출발지 MAC | [ IP 패킷: 출발지 IP | 목적지 IP | 데이터 ] ]
```

**"같은 네트워크"란? (서브넷과 CIDR)**

- `192.168.0.100/16`에서 `/16`은 "앞의 16비트가 네트워크 번호"라는 뜻이다.
- 그래서 `192.168.x.x` 전체(65,536개)가 **같은 네트워크**다.
- `10.100.0.1/24`는 앞 24비트가 네트워크 번호다. `10.100.0.0~10.100.0.255`(256개)가 같은 네트워크다.
- 같은 네트워크 안에서는 라우터 없이 **직접** 통신한다. 다른 네트워크는 라우터를 거쳐야 한다.

**ARP: IP를 MAC으로 바꾸기**

- 프레임을 보내려면 목적지 MAC을 알아야 한다. 그런데 보통 아는 건 IP뿐이다.
- 그래서 네트워크 전체에 **"192.168.0.1 가진 사람, MAC 알려줘"** 라고 브로드캐스트한다. 이게 ARP다.
- 결과는 캐시에 저장된다 (`ip neigh`).
  ```
  192.168.0.1 dev enp7s0 lladdr 88:36:6c:c1:0b:ff REACHABLE   ← 공유기의 MAC
  ```

### 2. 스위치와 라우터, 그리고 공유기

**스위치 (L2)**

- 포트가 여러 개 있는 상자다. **IP를 전혀 모른다.**
- 프레임이 들어오면 출발지 MAC을 보고 "이 MAC은 3번 포트에 있구나"를 기억한다. 이 표를 FDB(MAC 테이블)라고 한다.
- 목적지 MAC이 있는 포트로만 프레임을 내보낸다. 모르는 MAC이나 브로드캐스트는 모든 포트로 뿌린다.
- **스위치에는 라우팅 테이블이 없다.** "업링크 포트"도 스위치 입장에서는 그냥 포트 중 하나다.

**라우터 (L3)**

- **네트워크마다 NIC(인터페이스)이 하나씩** 있고, 각 NIC에 IP가 있다.
- 한쪽 NIC으로 들어온 패킷의 목적지 IP를 보고, 라우팅 테이블에 따라 다른 NIC으로 내보낸다.
- 핵심: **라우터는 두 네트워크 "사이"에 서 있다.** 두 네트워크에 각각 발을 하나씩 딛고 있다.

**집 공유기 = 여러 장비를 한 상자에 넣은 것**

```
 ┌────────────── 집 공유기 ──────────────────────┐
 │  WAN 포트 ── [라우터 + NAT] ── [스위치] ── LAN 포트 1,2,3,4
 │  (공인 IP)       192.168.0.1     │           │
 │                 [DHCP 서버] ─────┘           └── 데스크톱(192.168.0.100)
 └───────────────────────────────────────────────┘
```

- LAN 포트 4개는 **스위치**다.
- 공유기 내부의 라우터가 이 스위치에 `192.168.0.1`이라는 발을 딛고 있다. 반대쪽 발은 WAN 포트(인터넷)다.
- 여기에 NAT와 DHCP 기능이 붙어 있다.
- **우리 설계에서 nixos-desktop이 하는 일이 정확히 이것이다.** 호스트가 VM들을 위한 **작은 공유기**가 된다.

### 3. 라우팅 테이블

**라우팅 테이블은 인터페이스별이 아니라 "호스트 전체에 하나"다**

- 라우팅 테이블은 **호스트 커널 전체가 쓰는 표**다 (정확히는 `main` 테이블).
- 각 줄이 "이 목적지로 가려면 **어느 인터페이스로**, **누구에게** 넘겨라"를 적는다.
- 인터페이스는 표의 **내용물(출구)** 이지, 표의 주인이 아니다.

현재 nixos-desktop의 표 (`ip route`):

```
default via 192.168.0.1 dev enp7s0 proto dhcp src 192.168.0.100 metric 1002
192.168.0.0/16 dev enp7s0 proto dhcp scope link src 192.168.0.100 metric 1002
```

| 단어 | 뜻 |
|---|---|
| `default` | 목적지 `0.0.0.0/0`. **다른 줄에 안 걸리는 모든 목적지**. |
| `192.168.0.0/16` | 목적지가 이 대역이면 이 줄을 쓴다. |
| **`via 192.168.0.1`** | **다음 홉(next hop, 게이트웨이).** "이 패킷은 192.168.0.1에게 넘겨라. 그다음은 그 라우터가 알아서 한다." |
| `dev enp7s0` | **어느 인터페이스로 내보낼지**. |
| `scope link` (`via` 없음) | 목적지가 **이 선에 직접 붙어 있다**. 게이트웨이 없이 목적지 자체에 ARP를 해서 바로 보낸다. |
| `proto dhcp` / `proto kernel` | 이 줄을 누가 넣었는지. DHCP 클라이언트 / 커널(IP 부여 시 자동). |
| `src 192.168.0.100` | 이 경로로 나갈 때 기본으로 쓸 출발지 IP. |
| `metric` | 같은 목적지에 경로가 여러 개면 숫자가 낮은 쪽을 쓴다. |

**경로 고르는 규칙: Longest Prefix Match**

- 목적지 IP에 맞는 줄이 여러 개면, **가장 구체적인(prefix가 긴) 줄**을 쓴다.
- 예: 목적지 `192.168.0.147` → `/16` 줄과 `default(/0)` 줄이 둘 다 맞는다. `/16`이 더 구체적이니 이걸 쓴다. 결과는 "직접 전달".
- 예: 목적지 `1.1.1.1` → `default`만 맞는다. 결과는 "192.168.0.1에게 넘김".

**`via`의 핵심: 목적지 IP는 그대로, 목적지 MAC만 바뀐다**

`1.1.1.1`로 보낼 때 프레임:

```
 목적지 MAC = 88:36:6c:c1:0b:ff  (공유기. via 192.168.0.1을 ARP로 찾은 결과)
 출발지 MAC = enp7s0 자신의 MAC
 목적지 IP  = 1.1.1.1           (최종 목적지. 안 바뀜)
```

- "via"는 **다음에 받을 사람의 IP**다. 그 IP를 ARP로 MAC으로 바꿔서 프레임의 목적지 MAC에 쓴다.
- 패킷은 라우터를 하나 지날 때마다 **새 프레임에 다시 담긴다.** MAC은 매번 바뀌고, IP는 그대로 간다 (NAT만 예외).

**참고: tailscale은 별도 테이블을 쓴다 (정책 라우팅)**

- `ip rule`을 보면 `5270: from all lookup 52`가 있다. main 테이블보다 **먼저** 52번 테이블을 본다.
- 52번에는 `100.64.0.1 dev tailscale0` 같은 tailnet 경로가 들어 있다.
- 조회 명령:
  ```bash
  ip rule                    # 어떤 테이블을 어떤 순서로 볼지
  ip route show table 52     # tailscale 테이블
  ip route show table all    # 모든 테이블
  ```

### 4. 리눅스 브리지의 정체 (가장 헷갈리는 부분)

**리눅스 브리지 `br-vm`은 두 가지 역할을 동시에 한다.**

1. **스위치 그 자체.** 포트가 달린 가상 스위치.
2. **호스트가 그 스위치에 꽂은 NIC.** `br-vm`이라는 이름의 인터페이스가 곧 "호스트 쪽 포트"다. 그래서 `br-vm`에 IP(10.100.0.1)를 줄 수 있다.

실물로 나누면:

- **스위치 본체** = br-vm (역할 1)
- **스위치에 꽂힌 호스트의 랜선** = br-vm 인터페이스 (역할 2), IP 10.100.0.1
- **스위치에 꽂힌 VM의 랜선** = tap 장치 (`vnet0`, `vnet1`)
  - tap은 **가상 랜선의 한쪽 끝**이다. 반대쪽 끝은 QEMU 프로세스가 쥐고 있고, VM 안에서는 NIC으로 보인다.
  - VM을 켜면 libvirt가 tap을 만들어서 br-vm의 포트로 꽂는다.

### 5. 서버실 비유로 그리기

핵심: **enp7s0은 스위치 아래에 꽂힌 게 아니라, 라우터 PC의 반대편 NIC이다.**

**우리 설계 (내부 브리지 + 라우팅 + NAT)**

```
 [집 공유기 192.168.0.1]
        │ 랜선
        │
   ┌────┴──────────── 라우터 PC (= nixos-desktop 호스트) ────────────┐
   │ NIC-A: enp7s0   192.168.0.100/16   ← WAN쪽 발                    │
   │                                                                 │
   │        [라우팅 테이블 + NAT + DHCP 서버]                          │
   │                                                                 │
   │ NIC-B: br-vm    10.100.0.1/24      ← LAN쪽 발                    │
   └────┬────────────────────────────────────────────────────────────┘
        │ 랜선 (br-vm 인터페이스)
        │
   ┌────┴──── L2 스위치 (= br-vm 브리지) ────┐
   │ 포트1          포트2          포트3     │
   └──┬──────────────┬────────────────────────┘
      │ 랜선 (vnet0)  │ 랜선 (vnet1)
 [서버: win-game] [서버: win-bank]
  10.100.0.10      10.100.0.20
```

- 스위치(br-vm)의 "업링크"는 라우터 PC의 LAN쪽 NIC(br-vm 인터페이스)에 꽂혀 있다.
- 라우터 PC의 **다른 NIC**(enp7s0)이 집 공유기에 꽂혀 있다.
- 그래서 **enp7s0은 스위치에 꽂히지 않는다.** 라우터 PC를 사이에 두고 반대편에 있다.
- 스위치에는 라우팅 테이블이 없다. 라우팅은 라우터 PC(호스트)가 한다.

**"브리지 아래에 enp7s0"을 두는 구조 = Flat 브리지**

```
 [집 공유기 192.168.0.1]  ← 라우터는 이것 하나뿐
        │ 랜선 (enp7s0)
   ┌────┴──── L2 스위치 (= br0 브리지) ──────────────────┐
   │ 포트: enp7s0   포트: br0(호스트)   포트: vnet0  vnet1 │
   └──────────────────┬─────────────────┬──────┬─────────┘
                 [호스트]           [win-game] [win-bank]
             192.168.0.100        192.168.0.x  192.168.0.y  ← 공유기가 DHCP로 줌
```

- br0은 **집 공유기의 스위치를 연장한 것**이 된다.
- 호스트는 라우터가 아니라 **그냥 스위치에 꽂힌 기기 하나**가 된다. 라우팅과 NAT는 집 공유기가 한다.
- 호스트 IP가 enp7s0에서 br0으로 옮겨가야 한다. 스위치 포트가 된 NIC은 IP를 가질 수 없기 때문이다. 그래서 적용할 때 SSH가 끊길 위험이 있다.

**두 구조의 차이는 "enp7s0을 스위치에 꽂느냐, 라우터의 반대편 발로 쓰느냐"다.**

### 6. 자주 헷갈리는 질문

**Q. VM의 기본 게이트웨이 10.100.0.1은 Windows 안에서 설정해야 하나?**

아니다. DHCP가 자동으로 알려준다. 호스트의 DHCP 서버가 한 번에 주는 정보:

- IP 주소: `10.100.0.10` (MAC 예약)
- 서브넷 마스크: `255.255.255.0` (= /24)
- **기본 게이트웨이: `10.100.0.1`** (DHCP option 3, "router")
- DNS 서버: 예) `192.168.0.1` 또는 `1.1.1.1` (DHCP option 6)

Windows는 이걸로 자기 라우팅 테이블을 만든다 (`route print`):

```
0.0.0.0        0.0.0.0        10.100.0.1   10.100.0.10   ← default via 10.100.0.1
10.100.0.0     255.255.255.0  연결됨        10.100.0.10   ← 직접 연결
```

DHCP 없이 Windows에 IP를 직접 입력하는 방식(정적 IP)이라면, 게이트웨이도 직접 입력해야 한다.

**Q. 호스트에서 VM에 접근하려면 10.100.0.0/24 경로가 어디에 등록되어야 하나?**

`dev br-vm`으로 등록되어야 하고, 이건 자동으로 생긴다. `br-vm`에 `10.100.0.1/24`를 부여하는 순간 커널이 이 줄을 넣는다.

```
10.100.0.0/24 dev br-vm proto kernel scope link src 10.100.0.1
```

설정 후 호스트의 전체 표:

```
default via 192.168.0.1 dev enp7s0 ...                         ← 인터넷은 공유기로
10.100.0.0/24 dev br-vm proto kernel scope link src 10.100.0.1 ← VM 대역은 br-vm으로 직접
192.168.0.0/16 dev enp7s0 ... scope link ...                   ← 집 LAN은 enp7s0으로 직접
```

**Q. `via` 있는 줄과 없는 줄은 프레임이 어떻게 다른가?**

바뀌는 건 **목적지 MAC**이다. 출발지 MAC은 항상 나가는 인터페이스 자신의 MAC이다. 두 경우 모두 ARP를 하고, 차이는 **누구의 MAC을 찾느냐**다.

| | `default via 192.168.0.1 dev enp7s0` | `192.168.0.0/16 dev enp7s0 scope link` |
|---|---|---|
| ARP 대상 | **게이트웨이 IP** (192.168.0.1) | **목적지 IP 자체** (예: 192.168.0.147) |
| 목적지 MAC | 공유기 MAC | 목적지 기기의 MAC |
| 출발지 MAC | enp7s0의 MAC | enp7s0의 MAC |
| 목적지 IP | 최종 목적지 (예: 1.1.1.1) | 최종 목적지 (192.168.0.147) |

**Q. 다음 홉으로 보내려면 항상 `via`가 있어야 하나?**

- `via` 있음 = "목적지가 같은 링크에 없으니 **다음 홉 라우터에게** 넘긴다."
- `via` 없음 = "목적지가 **이 링크에 직접 붙어 있다**(directly connected)."
- `via`가 없는 줄도 **L3 라우팅 결정**이다. 커널이 이 줄을 고르는 것까지는 L3이고, 그 링크 위에서 전달하는 게 L2(ARP + 스위칭)다.
- 예외: 점대점(point-to-point) 링크. `100.64.0.1 dev tailscale0`처럼 L3 터널(tun, WireGuard)은 MAC도 ARP도 없다. 링크 건너편이 곧 다음 홉이라 `via`가 필요 없다.
- 정리: 이더넷처럼 여러 기기가 붙는 링크에서는 "다른 서브넷 = `via` 필요, 같은 서브넷 = `via` 없음"이 맞다. 터널은 예외다.

**Q. VM의 tap을 br-vm에 꽂는 건 어떻게 하나? 손으로도 되나?**

된다. libvirt가 VM을 켤 때 하는 일:

1. `/dev/net/tun`을 열어서 tap 장치(`vnet0`)를 만든다. 받은 파일 디스크립터(fd)를 QEMU에 넘긴다.
2. `vnet0`을 `br-vm`에 꽂고 켠다. 이게 "랜선 연결"이다.
3. QEMU는 그 fd로 프레임을 읽고 쓴다. VM 안에서는 virtio NIC으로 보인다.

손으로 하면:

```bash
sudo ip tuntap add dev tap0 mode tap user desktop   # 랜선 만들기
sudo ip link set tap0 master br-vm                  # 스위치(br-vm)에 꽂기
sudo ip link set tap0 up
qemu-system-x86_64 ... \
  -netdev tap,id=n0,ifname=tap0,script=no,downscript=no \
  -device virtio-net-pci,netdev=n0,mac=52:54:00:64:00:0a
```

- `brctl`(bridge-utils)은 예전 도구이고 deprecated다. 요즘은 `ip link ... master`로 꽂고 `bridge link`, `bridge fdb`로 본다.
- Docker의 **veth**는 양쪽 끝이 **둘 다 커널 인터페이스**다. 한쪽을 컨테이너의 네트워크 네임스페이스로 옮긴다. 컨테이너는 호스트 커널을 같이 쓰니까 네임스페이스로 격리한다.
- **tap**은 한쪽 끝만 커널 인터페이스다. 반대쪽 끝은 **사용자 공간 프로세스(QEMU)가 쥔 fd**다. VM은 자기 커널이 따로 있어서 네임스페이스가 필요 없다.
- 브리지에 꽂는 방식(`master br-vm`)은 둘 다 같다.

### 7. 패킷 따라가기

**① win-game → 1.1.1.1 (인터넷으로 나가기)**

| 구간 | 목적지 MAC | 출발지 IP | 목적지 IP | 일어난 일 |
|---|---|---|---|---|
| VM → br-vm | br-vm의 MAC | 10.100.0.10 | 1.1.1.1 | VM이 default via 10.100.0.1을 보고, 게이트웨이 MAC으로 보냄 |
| 호스트 내부 | – | – | – | 목적지가 자기 IP가 아님 → **forward**. `default via 192.168.0.1 dev enp7s0` 선택 |
| 호스트 → 공유기 | 공유기 MAC | **192.168.0.100** | 1.1.1.1 | nftables MASQUERADE가 출발지를 호스트 IP로 바꿈. conntrack이 기록 |
| 공유기 → 인터넷 | (ISP 장비) | **공인 IP** | 1.1.1.1 | 공유기도 한 번 더 NAT (**이중 NAT**) |

- 응답은 반대 순서로 돌아온다. 공유기가 192.168.0.100으로 되돌리고, 호스트의 conntrack이 기록을 보고 목적지를 10.100.0.10으로 되돌려서 br-vm으로 보낸다.
- **왜 NAT가 필요한가?**
  - 공유기는 10.100.0.0/24라는 대역이 있는지 모른다. 공유기의 라우팅 테이블에 그 경로가 없다.
  - NAT 없이 출발지 10.100.0.10으로 나가면, 응답을 어디로 보낼지 몰라서 버린다.
  - NAT로 "호스트가 보낸 것처럼" 만들면, 공유기는 호스트에게만 답하면 된다.
  - 대안: 공유기에 "10.100.0.0/24 via 192.168.0.100" 정적 경로를 넣으면 NAT 없이 순수 라우팅이 된다. 다만 공유기 설정은 repo 밖이라 NAT를 택했다.

**② 호스트가 "라우터"가 되려면: `ip_forward`**

- 현재 nixos-desktop은 `net.ipv4.ip_forward = 0`이다 (2026-09-28 확인).
- 이 상태에서 리눅스는 **자기 IP로 온 패킷만 받고, 남의 패킷은 버린다.** 일반 PC의 기본 동작이다.
- `1`로 바꿔야 "남의 패킷을 다른 인터페이스로 넘겨주는" 라우터가 된다. tailscale 서브넷 라우터에도 필요하다.

**③ 맥북 → win-game (Moonlight)**

1. 맥북의 tailscale이 "10.100.0.0/24는 nixos-desktop이 광고한 대역"이라는 걸 안다. 그래서 WireGuard 터널로 보낸다.
2. 패킷이 호스트의 `tailscale0`으로 들어온다. 목적지 10.100.0.10은 호스트 자신이 아니다 → forward. `10.100.0.0/24 dev br-vm` 경로로 나간다.
3. tailscale은 기본적으로 출발지를 호스트 IP로 SNAT한다. 그래서 VM은 10.100.0.1에서 접속이 온 것으로 본다.
4. VM은 10.100.0.1이 같은 네트워크니 직접 응답한다. VM은 tailnet(100.64.x) 경로를 몰라도 된다.

### 8. 용어 대응표

| VirtualBox | QEMU/libvirt | 구조 | 호스트→VM 접속 | VM→인터넷 |
|---|---|---|---|---|
| Bridged | bridge (물리 NIC 포함) | 집 LAN 스위치 연장 | ○ | ○ (공유기가 라우팅) |
| NAT | user-mode (slirp/passt) | 사용자 공간 가짜 네트워크 | ✕ | ○ |
| **Host-only** (192.168.56.x) | isolated network | IP 있는 브리지, 외부 경로 없음 | ○ | ✕ |
| NAT Network | NAT network (virbr0) | IP 있는 브리지 + 라우팅 + MASQUERADE | ○ | ○ |
| – | **우리 설계 (br-vm)** | Host-only 브리지에 라우팅 + NAT + DHCP를 더함 | ○ | ○ |

**한 줄 요약:** 우리 설계는 "Host-only 네트워크(192.168.56.x 자리에 10.100.0.x)에, 호스트가 공유기처럼 라우팅과 NAT를 해주는 것"이다.

## 1-2. "`vfio-pci.ids=...`로 1660S를 호스트에서 떼어낸다"는 뜻

**리눅스가 PCI 장치에 드라이버를 붙이는 방식**

- 부팅할 때 커널이 PCI 버스를 훑으면서 각 장치의 `vendor:device` ID를 읽는다. 1660S는 `10de:21c4`다.
- 각 드라이버는 "나는 이 ID들을 담당한다"는 목록을 가지고 있다. 지금은 `nouveau`가 `10de:21c4`를 가져갔다.
- 장치 하나에는 드라이버가 **하나만** 붙을 수 있다.

**vfio-pci가 하는 일**

- `vfio-pci`는 그래픽 기능이 없는 "껍데기 드라이버"다. 장치를 붙잡아 두기만 한다.
- 그리고 그 장치를 **사용자 공간 프로그램(QEMU)에 안전하게 넘겨주는 통로**(`/dev/vfio/6`)를 연다.
- 커널 파라미터 `vfio-pci.ids=10de:21c4,10de:1aeb,10de:1aec,10de:1aed`는 "이 네 ID는 nouveau보다 먼저 네가 가져가라"는 뜻이다.
- 그래서 vfio-pci를 initrd에서 일찍 로드하고, nouveau는 블랙리스트에 넣는다.

**IOMMU가 필요한 이유**

- GPU는 DMA로 메모리를 직접 읽고 쓴다. VM 안의 드라이버가 GPU에게 "물리 주소 X에 써라"라고 시키면, 그대로는 **호스트 메모리를 덮어쓸 수 있다.**
- IOMMU는 장치용 MMU다. 장치가 보는 주소를 VM의 메모리로만 변환하고, 그 밖은 막는다.
- IOMMU 그룹은 "하드웨어적으로 서로 격리할 수 없는 장치 묶음"이다. 그래서 그룹 6의 네 기능을 **통째로** 넘겨야 한다.

**결과**

- 호스트는 1660S를 더 이상 쓰지 않는다. 화면 출력도 없어진다.
- VM 안의 Windows가 NVIDIA 정식 드라이버로 실제 GPU를 쓴다.
- 확인 방법: `/sys/bus/pci/devices/0000:01:00.0/driver`가 `vfio-pci`를 가리키면 성공이다.

## 1-3. btrfs 서브볼륨을 쓰는 이유

**서브볼륨이란**

- 하나의 btrfs 파일시스템 안에 있는 **독립된 디렉터리 트리**다.
- 파티션처럼 따로 마운트하고 따로 스냅샷할 수 있다.
- 하지만 크기를 미리 나누지 않는다. 모든 서브볼륨이 디스크 전체 공간을 **같이** 쓴다.
- 지금 `/`, `/nix`, `/home`, `/var`가 각각 서브볼륨이다. 그래서 `df`에서 네 곳 모두 466G로 똑같이 보였다.

**VM 이미지에 전용 서브볼륨을 쓰는 이유**

1. **스냅샷 경계.** btrfs 스냅샷은 서브볼륨 단위로 뜨고, 다른 서브볼륨은 포함하지 않는다.
   - `/var`를 스냅샷할 때 100GB짜리 VM 이미지가 딸려 들어가지 않는다.
   - 반대로 나중에 restic 백업을 할 때는 **VM 이미지 서브볼륨만** 스냅샷을 떠서 restic에 넘기면 된다. VM을 몇 초만 멈추면 일관된 이미지가 나온다.
2. **CoW 끄기.** btrfs는 기본이 Copy-on-Write다. 블록을 덮어쓰지 않고 새 위치에 쓴 뒤 포인터를 바꾼다.
   - VM 디스크 이미지처럼 큰 파일 한가운데를 계속 조금씩 고쳐 쓰면, 파일이 수만 조각으로 흩어진다(단편화). 성능이 떨어진다.
   - 그래서 이미지 디렉터리에 `chattr +C`(nodatacow)를 건다.
   - 주의 1: 대부분의 btrfs 마운트 옵션은 서브볼륨별이 아니라 **파일시스템 전체**에 적용된다. 그래서 `nodatacow` 마운트 옵션 대신 디렉터리 속성을 쓴다.
   - 주의 2: nodatacow 파일은 체크섬과 압축이 꺼진다. VM 이미지에는 흔히 받아들이는 트레이드오프다. 게스트(NTFS)가 자체적으로 관리하기 때문이다.
3. **관리 단위.** `btrfs subvolume show`로 용량을 확인하고, 필요하면 quota를 걸 수 있다.
